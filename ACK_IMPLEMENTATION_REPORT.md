# ACK Stabilization Implementation Report

## Baseline and safety

- Implementation baseline: `ack` commit `6d10a1d08d6ff0daf25f8e9d2ddf68754e34a034`.
- Recovery branch: `ack-stabilization-20261107`, created from that commit.
- The `cms1` branch remains unchanged.
- Physical devices, production services, and production databases are out of scope.

## Stage 1 architectural decisions

### Offline queue: Option A, CMS1-local bookkeeping

The queue records are generated by CMS1 after local verification handling. They contain a queue ID, operation, gate/vehicle/token details, and a JSON summary of the decision. Repository consumers are CMS1 `pending()`/status helpers and the dashboard's generic table view; the CMS2 receiver does not consume queue entries. The deployment documentation describes CMS2 as a database mirror. The radio payload already exports the source tables containing verification and operational history, but does not serialize `offline_queue`.

Therefore the queue is treated as local audit/bookkeeping, not an independent CMS2 business-event outbox. A successful database-mirror ACK must not change its status or imply remote receipt. New entries will be marked locally complete after the local verification database work has committed. Existing historical statuses will not be rewritten. No CMS2 inbox table or protocol is warranted by the current product contract.

### LoRa transmit completion and pacing

The pinned `sandeepmistry/LoRa@^0.8.0` API declares `endPacket(bool async = false)`; its default implementation waits for TX-done. The CMS1 firmware calls `endPacket()` with no argument, so the firmware does not process a subsequent serial command during radio transmission. The Python publisher currently writes frames at 0.5-second intervals without waiting for firmware completion, which can accumulate commands in the serial receive buffer.

The selected correction is to retain blocking, serialized firmware transmission and pace Python command writes by the estimated airtime of the actual serialized RF payload, UART line time, and a small guard interval. This avoids introducing a TX_DONE protocol. Pacing is an engineering estimate; controlled hardware validation remains required.

### Transaction and ACK decisions

Reconciliation will use one SQLite connection and one transaction for the whole payload. Payload/table/column shapes will be validated before writes; any write failure will roll back the transaction before the receiver can send a NACK. A positive ACK will remain emitted only after reconciliation returns from commit.

CMS1 firmware keeps receiving on CH2 after unrelated packets and terminates
its wait only for a complete, strictly validated `SYNC_ACK` with the active
transfer ID (positive or negative), or the receive deadline. The frame types
and transfer-ID field are retained.

## Implementation and validation results

### Reconciliation atomicity

`scripts/reconciliation.py` now resolves the configured `DB_PATH`, validates
all table names, row shapes, keys, timestamps, and required schema columns
before applying changes, then runs the full payload under one
`BEGIN IMMEDIATE` transaction. Any write error rolls back all earlier table
changes. CMS2 emits a negative ACK only after the rollback is complete; it
emits a positive ACK only after the transaction commits. A dry run rolls back
and does not invoke clone-alert callbacks. The original one-table
`lww_upsert()` helper remains available for single-table callers.

### Transfer and queue semantics

`lora_sync_server.py` builds at most 4 KiB per batch from a CMS1 SQLite change
journal. Every row change is keyed by a monotonic journal sequence rather than
timestamp, avoiding timestamp ties and primary-key cursor ambiguity. Batches
include their cursor range, per-transfer ID, byte/chunk bounds, and SHA-256;
the payload includes changed rows and explicit deletions. The publisher keeps
only one bounded batch's frames in memory.

CMS1 persists `acked_seq` and prunes the acknowledged journal range in one
transaction only after a strict positive ACK for the active END phase. NACKs,
malformed/duplicate critical fields, wrong IDs, stale/out-of-phase ACKs, and
timeouts do not advance it. CMS2 validates the batch and applies upserts and
deletions in one transaction before sending the ACK. Replays after a lost ACK
are idempotent. A single over-limit row creates a persistent `sync_errors`
diagnostic with table and primary key, blocks cursor advancement, and can be
resolved by correcting or deleting that row; the resolved state is updated
only after its replacement/delete batch is acknowledged.
Journal-backed reconciliation also accepts an incoming CMS1 row on equal
timestamps; legacy payloads without journal metadata retain the previous
strict-newer timestamp rule.

CMS1's `init_db.py` adds the local journal, checkpoint, diagnostic tables, and
row-change triggers and seeds existing rows once. The CMS2 installer invokes
`init_db.py --mirror-only`, preventing unused CMS1 journal triggers from
accumulating on the mirror database. The receiver enforces the same
4 KiB/41-chunk cap and still requires `VVS_SERIAL_PORT` with bounded reconnect.

The offline queue is local bookkeeping, not a CMS2 outbox. New entries are
marked `done` when enqueued after local verification database work commits.
Sync ACKs do not update queue status, and historical pending/sent records are
not migrated or rewritten. No queue schema change is made.

### Firmware, timing, and deployment configuration

CMS1 firmware uses a complete JSON parser for ACK responses. It rejects
malformed/trailing data, duplicate critical fields, nested substitutes, and
incorrect types; matching positive and negative ACKs terminate the radio wait
with distinct results. The Python publisher parses raw ACK JSON with duplicate
key detection and requires the active transfer ID and END-wait phase. CMS2
and CMS1 firmware explicitly configure the same radio profile. The Python
publisher paces each frame using estimated LoRa airtime, UART line time, and a
0.25 second guard; the host ACK deadline
accounts for END UART/RF time, firmware wait, and a scheduling margin.

The CMS2 systemd template loads a per-user environment file, joins `dialout`,
and restarts on failure. The installer refuses to enable the service until
`VVS_SERIAL_PORT` is configured; documentation recommends the host's
adapter-specific `/dev/serial/by-id/` path. Receiver reconnect/backoff handles
temporary disappearance but cannot establish that the configured path exists
or is stable on a particular host.

### Validation and compatibility status

The full Python suite passed **40 tests**. CMS1 `esp32dev` and CMS2
`nodemcuv2` PlatformIO builds succeeded; CMS1 used 21,600 bytes RAM and
283,841 bytes flash, and CMS2 used 28,360 bytes RAM and 271,287 bytes flash.
The CMS2 installer passed `bash -n`; `git diff --check` passed; CMS1 and CMS2
source/Arduino copies, including the CMS1 ACK parser header, match. Shared ACK
vectors ran against Python, and the firmware parser compiled, but the
environment has no native C++ test runner.

CMS1 firmware and Python publisher/listener must be installed as a matched
pair. CMS2 Python receiver and its service/environment setup must also be
updated together with the publisher for the new validation and deployment
behavior. CMS2 firmware retains the existing frame protocol, but its explicit
profile build is included in the candidate. Mixed-version deployment is not
certified. The candidate's protocol and installation details are in
`ACK_PROTOCOL_DOCUMENTATION.md`; repeatable validation and hardware-only
checks are in `ACK_TEST_REPORT.md`.

### Risks and release recommendation

- Hardware RF profile, packet loss, physical serial path, and actual target
  host behavior have not been tested.
- The firmware parser is purpose-built for the JSON grammar and current
  protocol. Shared vectors execute in Python, while firmware has compile
  validation but no native C++ vector runner.
- The fixed 15-second CMS1 ACK window must be validated against actual paired
  radios and representative CMS2 commit times. The 4 KiB batch cap bounds
  memory and retry scope, but at SF12 each 100-byte chunk still consumes
  roughly 7.9 seconds of airtime.
- The local queue's new `done` status changes the meaning of newly created
  queue rows from “awaiting remote sync” to “local bookkeeping complete.”
  Existing historical statuses are left intact.

Recommendation: **ready for controlled, non-production hardware validation
only**, subject to the final software validation results recorded in
`ACK_TEST_REPORT.md`. Do not redeploy to production until paired-device tests
confirm the complete transfer/ACK path and measured timings.
